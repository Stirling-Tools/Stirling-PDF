### R1 — rust-connection

**Subsystem map.** The desktop app connection/auth subsystem consists of: (1) `commands/connection.rs` — Tauri commands for managing connection mode, server config, and lock flags; (2) `commands/auth.rs` — authentication commands (login, OAuth, token management) with keyring/Tauri-store fallback; (3) `state/connection_state.rs` — single-file definition of `ConnectionState` with mode, server_config, lock_connection_mode; (4) `utils/paths.rs` — app data directory resolution and `system_provisioning_dir()` returning `/Library/Application Support/Stirling-PDF` on macOS.

**Evidence & recommendations (verbatim).**

- **R1-F1** (`commands/connection.rs:128`): `if already_locked { log::warn!("set_connection_mode called while lock_connection_mode=true — preserving connection settings, but marking setup as completed"); ... return Ok(()); }` — *Behavior is correct and intentional — lock prevents modification of mode/server_config while allowing setup_completed flag to be written.*
- **R1-F2** (`commands/connection.rs:297`): `store.set(LOCK_CONNECTION_KEY, serde_json::to_value(lock_flag)...);` — *This is the mechanism by which `stirling-provisioning.json` re-locks settings at startup — the flag is persisted to `connection.json` and survives restarts.*
- **R1-F3** (`commands/connection.rs:321`): `let locked = provisioning_path_is_admin_owned(&provisioning_path, system_dir.as_deref()); store.set(UPDATE_MODE_LOCKED_KEY, serde_json::json!(locked));` — *This is correct — user-placed provisioning files should not lock the UI permanently since the file is deleted after apply.*
- **R1-F4** (`utils/paths.rs:24`): `Some(PathBuf::from("/Library").join("Application Support").join("Stirling-PDF"))` — *Correct — `/Library` is the system-wide Application Support location requiring admin/root rights to write.*
- **R1-F5** (`commands/connection.rs:220`): `lock_flag` is extracted from provisioning but only applied to `connection.json` as a user-modifiable field; `update_mode_locked` is the only field derived from `provisioning_path_is_admin_owned()` — *This is the intended design — `lock_connection_mode` can be set by any provisioning file (user or admin), while `update_mode_locked` is admin-only.*
- **R1-F6** (`commands/connection.rs:274`): `let lock_flag = parsed.lock_connection_mode.unwrap_or(false); ... store.set(LOCK_CONNECTION_KEY, serde_json::to_value(lock_flag)...)` — *User-placed `stirling-provisioning.json` in `~/Library/Application Support/Stirling-PDF` can set `lock_connection_mode=true`, which will prevent future changes to `connection_mode` until the flag is manually cleared.*

**Lock enforcement points (Rust):** `commands/connection.rs:128`, `:142`, `:297`, `:342`, `:96`, `:124`.

**Notes (R1).** The `connection.json` lock mechanism works as follows: (1) a provisioning file (`stirling-provisioning.json`) in `/Library/Application Support/Stirling-PDF` on macOS is detected at startup; (2) its `lock_connection_mode=true` is written to `connection.json`; (3) on subsequent launches, `get_connection_config` reads `lock_connection_mode=true` and updates in-memory state; (4) any attempt to call `set_connection_mode` detects `already_locked=true` and returns early without modifying mode/server_config. The lock persists across restarts because it is stored in `connection.json` (the Tauri store), not just in the transient provisioning file. The key distinction: `update_mode_locked` is only set when the provisioning file comes from a system/admin path, while `lock_connection_mode` can be set by any provisioning file.

### R2 — frontend-signin

**Subsystem map.** Stirling PDF desktop sign-in / server-selection flow (Tauri shell + React, `frontend/editor/src/desktop/` + `src-tauri/`). Three cooperating layers: (1) **Rust store layer** (`src-tauri/src/commands/connection.rs`) persists `connection_mode`, `server_config.url`, `lock_connection_mode`, `setup_completed` to `connection.json` via tauri-plugin-store; `get_connection_config` reads, `set_connection_mode` writes (with a lock guard), `apply_provisioning_if_present` applies an MDM/Intune `stirling-provisioning.json` (forces mode=selfhosted + URL + lock), `is_first_launch`/`reset_setup_completion` drive onboarding. (2) **TS service layer** (`desktop/services/connectionModeService.ts`) singleton wraps the invokes: `switchToSaaS` (throws when locked), `switchToLocal` (preserves `server_config` when locked), `switchToSelfHosted` (no TS lock check — relies on the Rust guard), `testConnection` (9-stage diagnostics), `resetSetupCompletion` (no-op when locked); notifies subscribers on mode change. (3) **UI layer:** SetupWizard (step machine SaaSLogin→SaaSSignup→ServerSelection→SelfHostedLogin; `loadLockedConfig` short-circuits to SelfHostedLogin when locked), ServerSelection (the ONLY manual URL entry: TextInput + connection test + login-config fetch, plus a "last used server" localStorage shortcut), SignInModal (hosts SetupWizard via `stirling:open-sign-in` event; `locked` detail controls closability), DesktopOnboardingModal (first-launch welcome→sign-in), ConnectionSettings (Settings page: Sign In / Log Out only — NO server picker), AppProviders (boot: locked first-launch→selfhosted; JWT-expiry→local fallback only when NOT locked). Auto sign-in target is data-driven: self-hosted = `server_config.url` in `connection.json` (currently `https://cpubox.asg.ts.net:8443`); SaaS = `STIRLING_SAAS_URL` = `VITE_SAAS_SERVER_URL` = `https://auth.stirling.com` (`.env.desktop:12`). When `lock_connection_mode=true` the user CANNOT sign into other servers (all three layers block it); when false, ServerSelection's manual URL entry is reachable and any server can be chosen.

### R4 — security

**Subsystem map.** Stirling PDF desktop (Tauri) auth/connection subsystem. Token storage is layered: (1) primary = OS keyring via the `keyring` crate, service `"stirling-pdf"`, keys `"auth-token"`/`"refresh-token"` (`auth.rs:17-18`); (2) fallback = Tauri Store file `tokens.json` (`auth.rs:14,113-138`); (3) web-layer mirror = localStorage `"stirling_jwt"` (`authService.ts:96,146`). The keyring entry is a SINGLE slot NOT scoped per server URL. Connection config (mode, server URL, lock flag) lives in `connection.json` via Tauri Store (`connection.rs:13`). The lock is enforced by a Rust guard in `set_connection_mode` (`connection.rs:123-136`) plus frontend guards in `connectionModeService.ts` (138-140, 1259) and UI gating in SetupWizard/AppProviders. Login POSTs username/password via a reqwest client built with `danger_accept_invalid_certs(true)` (`auth.rs:436, 792`). Current state: `connection.json` has `connection_mode=selfhosted`, url=`cpubox:8443`, lock=true, and NO `user_info` key; `tokens.json` is empty (`{}`), so any live token resides only in the macOS keychain.
