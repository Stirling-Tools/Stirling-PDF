Startup & runtime performance — perf/lighthouse-score bc6ceaec6d

Branch perf/lighthouse-score at bc6ceaec6d, measured on the production build (frontend/editor/dist) served by tests/walkthrough/perf/audit-serve.mjs on localhost:4181 with the repo's stubbed API. Two independent instruments: Lighthouse (simulated throttling, cold load) and the repo's runtime harness (a real Chromium driving the UI, counters read over CDP while the harness itself is running, so its own overhead is included).

Verdicts

Startup bytes

401,676 B br JS + 10,786 B br CSS on the boot path = 412,462 B, −66,224 B br JS versus 467.9 KB br of JavaScript on the startup path at d0b14478cf. The previously published release of this report measured build 72c4ca2e3b at 455,138 B br on the same boot path, so this build is 42,676 B br smaller than that.

Lighthouse (5 cold runs each)

desktop median 97, mobile median 80. Simulated numbers; the mobile figure is bandwidth-bound.

Main thread / INP

1 long task(s) across 5 captures, 214 ms of blocking in total, longest single task 264 ms (the first document parse). Worst recorded interaction 32 ms, well inside the reviewer's 111 ms Event Timing budget.

DOM

Attached-element counts are flat when a scenario starts and ends on the same route (Settings 950 → 964 once, then flat across 5 and 12 cycles; picker +465 from revealing tiles). Earlier “+528 DOM nodes” readings were CDP's node counter including garbage.

Memory

Retention is bounded, not linear: Settings settles ~6 MB above baseline and is still ~7 MB at 12 cycles (lazy-chunk code, not a growing leak); a deleted file's cached page images are now pruned. Peaks are the real cost — one document load spikes 52–125 MB before settling.

What is deliberately not on the boot path

  • registry-DwIA86lH.js (144,039 B br) — the tool registry, loaded by the landing route, not by the entry.
  • All 28 per-family vendor-mantine-*.js chunks (0 in the boot closure) — a tool's Mantine components arrive with the tool.
  • Every tool chunk, the PDF viewer, pdfium wasm and the PDF worker.

Document & shell

  • dist/index.html: 203,972 B raw, containing the prerendered landing shell and an inline #shell-strings blob with 51 strings × 42 languages.
  • Prerender honesty: the shell carries exactly 51 text nodes and every one of the 42 delivered languages has exactly 51 strings, so the inline resolver repaints the real copy instead of dropping to React (verified statically, and the capture origin no longer appears in the markup).

  • Opening and closing the viewer six times on one document: each close returned to the library within +0.20 → +0.91 MB of library idle, the increments shrinking each cycle (0.06 / 0.30 / 0.19 / 0.09 / 0.07), with the DOM exactly flat at 1168 elements and 3 documents after every close — bounded, decelerating retention, not a leak. Only the first open produced a long task (206 ms, wasm/PDF parse); later cycles produced none.
  • How to read the viewer-document-cycle capture: that scenario starts on the empty landing and closes with one document sitting in the library, so its +14.3 MB is the one-time cost of having the library open with a document in it (measured directly at ≈11.8 MB for one 258.6 KB PDF), not five cycles of growth. The per-cycle open/close cost on the same build is the +0.20 → +0.91 MB above. The harness marks that capture unsupported because its baseline and closing samples are different states; this report says so instead of quoting the number as a leak.
  • Settings open/close is the same shape at a larger scale: settled JS heap +6.0 MB at 5 cycles and +6.97 MB at 12 (≈0.14 MB per extra cycle, asymptote ≈7 MB) while attached elements never move off 964. A heap snapshot attributes it to the lazy route's compiled code and bytecode, not to app objects.
  • Renderer-owned memory explains the rest of the churn residue: heap-snapshot deltas after a 6-file session were dominated by JSArrayBufferData (+19,924 KiB — pdfium's wasm memory only grows) and ExternalStringData (+6,793 KiB), with only 2,875 KiB in cached page images — the part the new prune can actually return.

Fixes shipped in this pass

problem the measurement exposedfixmeasured effect
Cached page images were capped by bytes only (1 GB, ~10 000 pages), and removing a file never evicted its images — heap snapshots showed 39 cached data:image/png;base64 strings / 2,875 KiB left after one 6-file add/delete session. 72c4ca2e3b: an entry cap of 512 images plus evictThumbnailsForFile(), reached from the file-removal path through a tiny pageImageCache seam so the pdfium render path stays out of the boot chunk. churn run: heap above an open empty library 14.24 → 13.66 MB, bytes released across six deletes 3.30 → 4.43 MB. The seam also kept the fix free of boot bytes (entry 578,815 B raw, closure 443,976 B br js, −863 B versus the pre-fix build).
The harness reported renderer garbage as retention (CDP node counts, unforced heap reads) and compared across a page reload. harness-only changes: forced-GC settled readings, attached-element counts read from the page, and a document-identity guard that marks a reloaded run incomparable instead of claiming growth. the false “+13.9 MB / +528 DOM nodes after one Settings cycle” became a bounded ~6 MB of lazy-chunk code with a flat DOM; two scenarios correctly moved to not-measured.

Method and limits

  • Runtime numbers come from the repo harness in frontend/editor/tests/walkthrough/perf/ against the production build at localhost:4181, with API calls served by the repo's Playwright route stubs and every run resetting to the same fixture.
  • Heap figures are Chromium's JS heap via CDP after two forced GCs; native/process memory and pdfium's wasm high-water mark are not visible to CDP, so a scenario that loads a document can show a large peak with little settled JS heap — both numbers are reported.
  • Retention is only claimed when the run started and ended on the same document, and is called bounded when the marginal cost per cycle shrinks (Settings: +6.0 MB at 5 cycles, +6.97 MB at 12).
  • Lighthouse can only model a throttled load; the mobile profile's FCP (≈3.6 s, stable across runs) is bandwidth-bound and dominates every mobile metric. Where a run's LCP element is React's own swap of the shell element, that run is jitter in the model, not a deterministic regression.
  • Gaps are listed per capture (metrics.unavailable) rather than omitted: React commit counts and Web Workers are unmeasurable in a production build, and window.totalMs was not recorded on two runs.
